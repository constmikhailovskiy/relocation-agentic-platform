## Вправа 1. Телефони в аргументах інструментів

**Проблема.** `redactMessages` чистив лише `content` — текст повідомлень. Але коли модель
викликає інструмент, вона пише аргументи в `tool_calls[].function.arguments`. На наступному
кроці агента вся історія, разом із цими аргументами, знову йде в модель. Тобто телефон,
який модель сама вставила в аргументи, повертався в хмару невідредагованим.

**Як ми працювали: спершу тест, потім код.**
1. Написали тест, що описує бажану поведінку (`policy.test.ts`, блок «Вправа 1»).
2. Запустили — він упав. Це доказ, що діра справжня, а тест її бачить.
3. Виправили код — тест позеленів.

Тест, що одразу проходить, нічого не доводить: можливо, він просто нічого не перевіряє.

**Код** (`policy.ts`, функція `redactMessages`):

```ts
const out = messages.map((m) => {
  const copy = { ...m, content: redactContent(m.content) } as ChatMessage;
  if (copy.role === "assistant" && copy.tool_calls) {
    copy.tool_calls = copy.tool_calls.map((tc) => {
      const r = redactText(tc.function.arguments);
      redactions += r.count;
      return { ...tc, function: { ...tc.function, arguments: r.text } };
    });
  }
  return copy;
});
```

Що тут відбувається, рядок за рядком:

- `messages.map((m) => { ... })` — пройти по кожному повідомленню і зібрати новий масив з того,
  що повертає функція. Старий масив не змінюється.
- `{ ...m, content: ... }` — **spread**: «скопіюй усі поля `m`, а `content` заміни». Ми не
  змінюємо оригінальне повідомлення, а робимо нове. Так безпечніше: хтось інший може ще
  користуватися оригіналом (наприклад, для запису в локальну модель без редагування).
- `as ChatMessage` — підказка компілятору «повір, це ChatMessage». Потрібна, бо після spread
  TypeScript втрачає точний тип.
- `copy.role === "assistant"` — **звуження типу**. `ChatMessage` — це «одне з чотирьох»
  (system, user, assistant, tool). Після цієї перевірки TypeScript знає, що це саме assistant,
  і дозволяє звернутись до `copy.tool_calls`. Для user-повідомлення такого поля немає, і без
  перевірки код би не скомпілювався.
- `&& copy.tool_calls` — і поле не порожнє.
- Вкладений spread `{ ...tc, function: { ...tc.function, arguments: r.text } }` — копіюємо
  виклик, всередині копіюємо `function`, і замінюємо лише `arguments`.

**Чому JSON не ламається.** Аргументи — це JSON-рядок, наприклад
`{"message":"Дзвоніть +380 67 123 45 67"}`. Ми замінюємо тільки цифри всередині лапок на
`[PHONE]`, лапок і дужок не чіпаємо. Тест перевіряє це явно через `JSON.parse(args)`.

**Що сказати на співбесіді.** «Редагування PII має покривати все, що йде в модель, а не лише
поле content. У мене була діра саме з аргументами інструментів — я спершу написав тест, що її
відтворює, потім закрив.»

## Вправа 2. Витрати по запуску

**Задача.** Додати `GET /v1/usage/runs/:runId` → скільки коштував конкретний запуск агента.

**Що знайшлось по дорозі (і це важливіше за сам ендпоінт).** `run_id` вигадує клієнт і
передає в заголовку `x-run-id`. Старий `spentOnRunUsd(runId)` рахував витрати лише за `run_id`.
Отже, якщо runtime і evals випадково взяли однаковий `run_id`, вони ділили б один бюджет.
Гірше: зловмисний клієнт міг би «з'їсти» бюджет чужого запуску. Тепер усі запити до запусків
фільтруються ще й за клієнтом.

**Код.** У `ledger.ts`:

```ts
runSummary(client: string, runId: string) {
  const row = this.db
    .prepare(`SELECT COALESCE(SUM(cost_usd), 0) AS s, COUNT(*) AS n, ...
              FROM llm_usage WHERE client = ? AND run_id = ?`)
    .get(client, runId) as { s: number; n: number; m: string | null };
  return { spentUsd: row.s, calls: row.n, models: row.m ? row.m.split(",") : [] };
}
```

- `?` у SQL — **плейсхолдери**. Значення `client` і `runId` підставляє драйвер, а не ми
  склеюванням рядків. Це захист від SQL-ін'єкцій: навіть якщо `runId` буде
  `x' OR '1'='1`, це просто рядок, а не частина SQL.
- `COALESCE(SUM(...), 0)` — якщо рядків немає, SUM поверне NULL; COALESCE замінить на 0.
- `as { s: number; ... }` — драйвер не знає типів наших колонок, тож описуємо форму рядка самі.
- `row.m ? row.m.split(",") : []` — **тернарний оператор**: «якщо m є — розбий на масив, інакше порожній масив».

У `app.ts`:

```ts
app.get("/v1/usage/runs/:runId", (c) => {
  const client = c.get("client");
  const runId = c.req.param("runId");
  const summary = ledger.runSummary(client.name, runId);
  if (summary.calls === 0) throw new PolicyError(404, "run_not_found", `Запуск ${runId} не знайдено`);
  return c.json({ runId, ...summary, maxRunUsd: client.maxRunUsd });
});
```

- `:runId` у шляху — параметр, Hono віддає його через `c.req.param("runId")`.
- `c.get("client")` — клієнт, якого раніше поклав middleware автентифікації. Ендпоінт сам
  ключ не перевіряє: це вже зроблено для всіх `/v1/*`.
- **Чому 404, а не 403 для чужого запуску.** 403 означало б «запуск існує, але не твій» —
  це вже витік інформації. 404 однаковий для «чужого» і «неіснуючого».
- `{ runId, ...summary, maxRunUsd }` — `runId` замість `runId: runId` (скорочений запис), а
  `...summary` розгортає поля підсумку в об'єкт відповіді.

**Тести** (три): свій запуск видно; чужий і неіснуючий дають однаковий 404; однаковий
`run_id` у двох клієнтів не ділить бюджет. Для цього в тестовий `setup` додано другого клієнта
`evals` з ключем `k2`.

## Вправа 3. Справжній Anthropic і кеш

Скрипт `scripts/cache-demo.ts` робить два запити з однаковим довгим початком (system-промпт з
усіма 80 оголошеннями + опис інструмента) і різними питаннями.

```bash
# термінал 1
pnpm gateway
# термінал 2
pnpm cache-demo               # з ANTHROPIC_API_KEY у .env
MODEL=mock pnpm cache-demo    # перевірити сам скрипт без ключа
```

**Що побачиш з haiku:** у першому запиті великий `cache_write`, у другому — великий
`cache_read` і менша вартість. Весь експеримент коштує частки цента.

**Як це влаштовано.** Провайдер кешує «префікс» запиту до позначки `cache_control`. Gateway
ставить її на system-промпт і на останній інструмент (етап 1, `providers/anthropic.ts`).
Наступний запит із тим самим префіксом читає його з кешу — у 10 разів дешевше за звичайний вхід.

**Тонкий момент, вартий згадки на співбесіді.** У довіднику є телефони, і gateway їх редагує
перед хмарою. Кеш працює лише тому, що редагування **детерміноване**: той самий текст щоразу
дає той самий результат. Якби ми підставляли випадкові мітки (`[PHONE_83af]`), префікс щоразу
був би іншим, і кеш би не спрацьовував. Приватність і вартість тут пов'язані.

**Якщо `cache_read = 0` у другому запиті:** префікс коротший за мінімальний розмір кешу для
моделі, або між запитами минуло більше 5 хвилин (стільки живе кеш за замовчуванням).

## Вправа 4. Хаос

```bash
FAIL_PROVIDER=anthropic pnpm gateway
curl -s localhost:8787/v1/chat/completions \
  -H 'authorization: Bearer dev-runtime-key' -H 'content-type: application/json' \
  -d '{"model":"haiku","messages":[{"role":"user","content":"Привіт"}]}' -i | grep -E "^HTTP|^x-gateway|error"
```

- **З Ollama і gpt-oss:** `200`, `x-gateway-model: gpt-oss`, `x-gateway-fallback-from: haiku`.
  У `/v1/usage` у записі буде `fallback_from: haiku`.
- **Без Ollama:** `502`, а в тексті помилки — обидві спроби.

**Що покращено.** Раніше клієнт бачив лише останню помилку: «ollama недоступний». On-call
подумав би, що проблема в Ollama, хоча першою впала haiku. Тепер gateway збирає історію спроб:

```ts
const attempts: string[] = [];
// ... у catch кожного кандидата:
attempts.push(`${entry.alias}: ${(e as Error).message}`);
// ... коли кандидати скінчились:
throw new HttpError(status, `Усі моделі недоступні — ${attempts.join("; ")}`);
```

Результат: `Усі моделі недоступні — haiku: chaos: anthropic вимкнено…; gpt-oss: ollama недоступний…`

- `string[]` — тип «масив рядків».
- `` `${a}: ${b}` `` — **шаблонний рядок**: підставляє значення змінних у текст.
- `(e as Error).message` — у `catch` TypeScript не знає тип помилки (це `unknown`: кинути можна
  що завгодно). `as Error` каже «вважай, що це Error», щоб взяти `.message`.

Тест «Вправа 4» перевіряє, що в повідомленні є обидві спроби.

## Вправа 5. Локальна модель

### Частина 1 (без Ollama): контрактні тести провайдера

Провайдер Ollama (`openai-compatible.ts`) не мав жодного тесту. Без самої Ollama його можна
перевірити, підмінивши глобальний `fetch` (`vi.stubGlobal`): тест сам вирішує, що «відповіла Ollama»,
і дивиться, що провайдер надіслав і як розібрав відповідь. Файл — `apps/gateway/test/ollama.test.ts`.

| Тест | До виправлення | Сенс |
| --- | --- | --- |
| reasoning з відповіді не губиться (complete) | зелений | характеризаційний: фіксує, що `looseObject` працює |
| reasoning з історії йде в наступний запит | зелений | те саме для зворотного напрямку |
| шматки reasoning у стрімі не губляться | **червоний** | баг: стрім пропускав лише `content` і `tool_calls` |
| (app.test) reasoning доходить до клієнта в SSE | **червоний** | баг у HTTP-шарі: невідомі дельти мовчки відкидались |

**Виправлення — три місця по ланцюжку «Ollama → провайдер → gateway → клієнт»:**

1. `providers/types.ts` — `reasoning?: string` у `StreamDelta` (внутрішня подія стріму).
2. `providers/openai-compatible.ts` — якщо в чанку є `delta.reasoning`, видаємо окрему подію.
3. `app.ts` + `ChatChunk` в `openai-types.ts` — загортаємо подію в SSE-чанк `{ delta: { reasoning } }`.
   Довжину міркувань додаємо до `partialChars`: це теж вихідні токени, і якщо стрім обірветься
   без usage, бюджет має їх врахувати.

**Чому це важливо.** Gateway — проксі, а головний ризик проксі — *тихо* губити поля, яких він не знає.
У gpt-oss міркування йдуть окремим полем, і без них модель плутається між кроками tool calling.
Звичайна відповідь це вже вміла (завдяки `looseObject`), а стрім — ні: там поля перекладаються
вручну, і про нове поле треба пам'ятати в кожній ланці.

**Припущення, яке треба звірити наживо:** назву поля `reasoning` у стрімі взято з документації Ollama.
На кроці 3 подивитись сиру відповідь `localhost:11434/v1/chat/completions` зі `stream: true`.

### Частина 2 (з Ollama) — далі

Встановлення Ollama, `ollama pull gpt-oss:20b`, прямий запит і через gateway,
`x-data-class: restricted` → `gpt-oss` відповідає, `haiku` — 403, tool calling наживо,
`FAIL_PROVIDER=anthropic` → fallback на `gpt-oss`, заміри швидкості.

## Шпаргалка синтаксису TypeScript з цього етапу

| Запис | Що означає |
| --- | --- |
| `const x = ...` | змінна, яку не можна перепризначити |
| `(a) => a + 1` | стрілкова функція |
| `async` / `await` | функція, що чекає на асинхронні операції (мережа, диск) без блокування |
| `{ ...obj, key: v }` | копія об'єкта з заміною поля |
| `obj?.field` | «якщо obj є — візьми поле, інакше undefined», без падіння |
| `a ?? b` | «a, а якщо a — null/undefined, то b» |
| `x!` | «я гарантую, що x не undefined» (обережно: якщо помилишся — впаде в рантаймі) |
| `x as T` | «вважай x типом T» — підказка компілятору, не перевірка |
| `if (m.role === "assistant")` | звуження типу: після перевірки TS знає точний варіант union |
| `string[]`, `Record<K, V>` | масив рядків; об'єкт-словник з ключами K і значеннями V |
| `` `текст ${змінна}` `` | шаблонний рядок |
| `z.infer<typeof Schema>` | тип TypeScript, виведений із zod-схеми |
