# Етап 4 — SSO, делегування, аудит

На етапах 2–3 сервери вірили заголовку `x-debug-sub`: назватися Оленою міг будь-хто. Тепер:

- **хто людина** — каже Keycloak (токен IdP), а runtime перевіряє підпис сам;
- **від чийого імені агент** — каже короткий токен, який підписав runtime як внутрішній STS
  (`sub` = людина, `act` = агент, `aud` = конкретний сервер, `run_id`, живе 5 хвилин);
- **що сталося** — журнал `audit_events` з хеш-ланцюжком, `pnpm audit:verify` ловить підробку.

`authorize` з таблицею з матриці ролей уже зроблено на етапі 2 (`packages/shared/src/policy.ts`, тести
`packages/shared/test/policy.test.ts`); тут вона просто отримує principal з перевіреного токена.

## Потік токенів

```mermaid
sequenceDiagram
  participant H as Олена
  participant K as Keycloak
  participant R as runtime (STS)
  participant M as MCP relocation
  H->>K: логін (пісочниця: пароль)
  K-->>R: токен людини (aud relocation-cli, mcp-relocation)
  R->>R: перевірити підпис, iss, aud → VerifiedUser; роль ∈ audience агента
  loop кожен HTTP-запит до MCP
    R->>M: Bearer <5 хв, sub=olena, act=agent:concierge@7, aud=mcp-relocation, run_id>
    M->>M: jwtAuth: ключ runtime, ES256, iss, aud, exp → authorize → аудит
  end
  H->>M: POST /approvals/:id/confirm з токеном IdP (не runtime!)
```

## 1. Аудит з хеш-ланцюжком (`packages/shared/src/audit.ts`)

**Що хочемо (тести `packages/shared/test/audit.test.ts`).**
- Кожен запис посилається на hash попереднього.
- `verify` ловить змінений рядок (`hash_mismatch`), видалений рядок у середині (`prev_mismatch`) і змінений
  рядок з перерахованим hash (ловиться на наступному).
- Обрізаний хвіст `verify` **не** бачить — це записано тестом як чесна межа.
- Два процеси пишуть в один файл одночасно — ланцюжок цілий.

**Як зроблено.**
- `hash = sha256(prev_hash + canonicalJson(подія))` (`audit.ts:83`). Канонічний JSON — той самий, що для `args_hash`.
- `append` (`audit.ts:95`): «прочитати останній hash → вставити» в одній транзакції `BEGIN IMMEDIATE`
  (`audit.ts:96`). Вона одразу бере блокування на запис, тож два процеси не прочитають той самий `prev_hash`.
- Тригери забороняють `UPDATE`/`DELETE` (`audit.ts:76`). У Postgres це була б роль без цих прав; у SQLite ролей
  немає. Від помилки в коді тригер захищає, від людини з доступом до файлу — ні (вона видалить тригер). Саме тому
  є ланцюжок: він не забороняє змінити, а робить зміну помітною.
- Аргументи пишуться лише хешем (`argsHash`): критерії пошуку з бюджетом — дані людини, у журналі їм не місце.
- Один файл `data/audit.db` на обидва сервери (`resolveAuditPath`): один ланцюжок, порядок подій між сервісами
  теж захищений. Відносний шлях — від кореня репо, бо `pnpm --filter` запускає кожен сервер у своїй теці.

**Де викликається.** `loadDeps` у `mcp/relocation/src/config.ts` і `mcp/listings/src/config.ts` — аудит тепер
обов'язковий параметр, живий сервер без нього не стартує. Події пише домен (`authorizeSearch`, `writeAudit`),
з `runId` з делегованого токена.

**Як переконатися самому.**
```bash
pnpm audit:verify                 # OK: ланцюжок цілий, записів N
pnpm audit:verify --run <run_id>  # усі кроки одного запуску: «хто і чому попросив перегляд»
```
Мутації: `BEGIN IMMEDIATE` → `BEGIN DEFERRED` дає `database is locked` у тесті двох процесів (SQLite не може
підняти спільне блокування до запису); читати `prev_hash` не з БД → 9 червоних тестів.

**Що бачили на мутації.** З `BEGIN DEFERRED` тест двох процесів падає з `database is locked`: транзакція
починається як читання, а коли настає час писати, інший процес уже записав — SQLite не може «підняти»
транзакцію до запису поверх застарілого знімка і відповідає помилкою одразу, не чекаючи `busy_timeout`.
`IMMEDIATE` бере право на запис на старті, тож другий процес просто чекає в черзі. (Точну механіку для режиму
WAL ми не розбирали; спостереження — саме помилка `database is locked`.)

## 2. Перевірка JWT у серверах (`packages/shared/src/auth.ts`)

**Що хочемо (тести `packages/shared/test/auth.test.ts`, `mcp/*/test/http.test.ts`).**
- Делегований токен → `{sub, act, runId}`.
- Відмова (→ 401) на кожне з: немає токена, чужий ключ, `aud` іншого сервера, чужий `iss`, прострочений,
  без `sub`, `alg: none`, а також `x-debug-sub` у JWT-режимі.
- Токен від IdP: `sub` там UUID, тож id працівника — з `preferred_username`.

**Як зроблено.** `jwtAuth` (`auth.ts:33`) → `jwtVerify` з `jose`: підпис, `iss`, `aud`, `exp`, **закріплені
алгоритми** (без цього можлива атака `alg: none` або підміна RS256 на HS256 з публічним ключем у ролі секрету).
Будь-яка помилка → `undefined`, причину зловмиснику не пояснюємо.

**Дві довіри в одному сервері** (`mcp/relocation/src/http.ts:35`, `buildServerAuth` у `auth.ts:88`):
- `/mcp` — лише токени runtime (публічний JWKS з файлу `.secrets/runtime-sts.jwks.json`);
- `/approvals/:id/confirm` — лише токени IdP (JWKS тягнемо з Keycloak, `auth.ts:95`).

Тест: токен від runtime з `sub=olena` і **без** `act` на `/approvals` → 401. Це закриває чесну межу етапу 3
(«підтвердження можна підробити») і відповідає на вправу 6 етапу 3.

**Режими.** `AUTH_MODE=jwt` за замовчуванням. `AUTH_MODE=debug` вмикає стару заглушку — лише для MCP Inspector,
сервер друкує попередження.

## 3. Runtime як STS (`apps/runtime/src/sts.ts`)

**Що хочемо (тести `apps/runtime/test/sts.test.ts`, `scenario-jwt.test.ts`).**
- Токен людини від IdP → `VerifiedUser` (id з `preferred_username`, ролі з `realm_access`, лише відомі).
- Роль має бути в `audience` агента: Богдан (`agent_builder`) Concierge не запустить.
- Делегований токен: `aud` одного сервера, 5 хвилин, `run_id` поточного ходу.
- Підписується **на кожен запит**: через 6 хвилин після підключення виклики працюють.

**Як зроблено.**
- `VerifiedUser` має «бренд» — поле з `unique symbol` (`sts.ts:9`). Створити такий об'єкт можна лише в
  `userVerifier`, тобто після перевірки підпису. Рядок `--as olena` у `mint` не передаси — TypeScript не дасть.
  *Етап 6:* з'явився другий шлях — `userFromGrant` для фонового Scout (грант, записаний, коли людина була поруч);
  `chat.ts` його не використовує. Див. [06-temporal.md](06-temporal.md).
- `connectTools` отримує `authHeaders(server)` і викликає її з обгортки `fetch` на кожен HTTP-запит
  (`mcp-tools.ts:46`). На етапі 3 заголовки задавались раз при підключенні — з токеном на 5 хвилин це не працює.
- `delegatedAuthHeaders` (`sts.ts:92`): `"relocation"` → `aud: "mcp-relocation"`; `run_id` бере з об'єкта
  `current`, який оновлює сесія на початку ходу.
- Токен людини далі не пересилається (token passthrough специфікація MCP забороняє): сервер бачить лише вузький
  токен для себе.

**Синтаксис TS, що з'явився вперше.**
- `declare const verified: unique symbol` — тип-символ, що існує лише на рівні типів. Поле `[verified]: true` в
  інтерфейсі робить тип «номінальним»: структурно схожий об'єкт без цього поля не підходить.
- `(r): r is Role => ...` — type guard: після `filter` TypeScript знає, що масив — `Role[]`, а не `unknown[]`.

**Мутації:** TTL година замість 5 хвилин, `aud` на обидва сервери, вимкнена перевірка audience, кешований токен
(«6 хвилин» і наскрізний тест) — кожна дає червоний тест.

## 4. Критерій готовності: Іван не бачить бюджет Олени

`apps/runtime/test/scenario-jwt.test.ts`, «Критерій етапу 4». Справжні JWT, справжні сервери в JWT-режимі:
Іван просить агента показати бюджет Олени; агент кличе `get_search` і `set_criteria`. Перевіряємо **не відповідь
моделі**, а те, що до неї дійшло: у жодному результаті інструмента немає `18000` чи `20000`; `get_search` повернув
лише `{id, employeeId, status}`, `set_criteria` — `forbidden`.

**Наживо з Keycloak (2026-11-18), усі сервіси в JWT-режимі, `haiku`:**
- Іван: «покажи бюджет, ліміт і критерії Олени; якщо не бачиш — постав їй 15000». `get_search` → лише статус,
  `set_criteria` → `forbidden`. Агент відповів: «бюджету, ліміту і критеріїв не бачу… бюджет не змінено». $0.0014.
- Богдан: `Агент concierge недоступний для bohdan (ролі: agent_builder)` — ще до першого виклику моделі.
- Невірний пароль: `Вхід ivan не вдався: Invalid user credentials`.
- Олена: критерії → пошук → шортлист → `shortlist_ready` → перегляд → `y` → підтвердження **справжнім токеном
  Keycloak** на `/approvals`. $0.0035.
- Журнал (`audit_events`), 9 записів, ланцюжок цілий:

| seq | хто | через кого | дія | рішення |
| --- | --- | --- | --- | --- |
| 1 | ivan | concierge@7 | get_search | allow_partial (manager_of) |
| 2 | ivan | concierge@7 | set_criteria | deny (manager_read_only) |
| 3–8 | olena | concierge@7 | get_search … request_viewing | allow (owner), один `run_id` |
| 9 | olena | — | confirm_viewing | allow (requester) |

- Підробка копії цього журналу (рядок 2: `deny` → `allow`) → `ПІДРОБКА: рядок seq=2 — вміст змінено`.

Клейми справжнього токена Keycloak (перевірили до запуску чату): `alg RS256`, `iss` realm-у, `aud
[relocation-cli, mcp-relocation]`, `preferred_username`, `realm_access.roles`, TTL 1800 с — усе, як чекає код.

## 5. Keycloak (`infra/`)

- `infra/docker-compose.yml` — Keycloak 26, `start-dev --import-realm`, лише `127.0.0.1:8080`.
- `infra/keycloak/relocation-sandbox-realm.json` — realm: ролі з матриці, сім демо-людей (пароль пісочниці
  `sandbox`), публічний клієнт `relocation-cli` лише з password grant і двома audience-mapper-ами.
- `scripts/test/keycloak-realm.test.ts` перевіряє realm офлайн: користувачі й ролі = `fixtures/employees.json`,
  `editUsernameAllowed: false` (інакше людина змінила б собі `preferred_username` і стала б кимось іншим),
  немає клієнтських секретів.

**Рішення про ролі.** Ролі живуть у двох місцях: Keycloak (для runtime: audience агента) і довідник людей
(для `authorize` на сервері). Тест realm-у тримає їх однаковими. У проді джерело одне — HR-система, яка
синхронізує IdP. Альтернатива — класти ролі в делегований токен і довіряти їм на сервері; тоді зламаний runtime
міг би підвищити собі права. Обрано: сервер ролям від runtime не вірить.

**Чому password grant.** Лише для CLI в пісочниці: застосунок бачить пароль, OAuth 2.1 цей grant прибирає.
У studio (етап 8) — Authorization Code + PKCE.


## Чесні межі

- **Журнал у режимі WAL — це три файли** (`audit.db`, `-wal`, `-shm`). Копія лише `audit.db` під час роботи сервісів
  порожня або застаріла — ми на це наступили. Бекап — через `sqlite3 .backup` або разом з `-wal`.
- **У CLI один процес тримає і токен людини, і ключ STS.** Розділення «підтверджує лише людина» справжнє,
  коли токен людини живе в studio (браузер), а runtime — окремий сервіс. У CLI зламаний процес runtime має обидва.
- **Обрізаний хвіст журналу непомітний.** Потрібен зовнішній якір: періодично публікувати останній hash.
- **Токен людини живе 30 хвилин** (`accessTokenLifespan` у realm); refresh не реалізовано. Довга сесія чату впаде
  на підтвердженні з 401.
- **Депровіжинінг** (вимкнули Олену в Keycloak → її фонові запуски зупиняються) — етап 6, разом із Temporal.
- **Відкликання ключа STS** — лише ротація (`pnpm sts:keygen --force`) і перезапуск серверів.
- **Runtime сам аудит не пише.** Старт і кінець запуску, виклики моделі, «ні» людини на HITL — лише в трейсі
  консолі, не в `audit_events`. У журналі є лише те, що бачать MCP-сервери.
- **Підтвердження перегляду в журналі без `run_id`** (людина приходить з токеном IdP, у ньому запуску немає),
  тож `audit:verify --run` його не покаже. Знайти можна за `resource` (id запиту).
- **Gateway досі автентифікує лише ключем клієнта** (`dev-runtime-key`), без токена людини.
- **Пароль у CLI видно при введенні** (простий `readline`). Для пісочниці — так; для чогось реального — ні.
- **`buildServerAuth` писався разом зі своїм тестом**, а не після червоного тесту; мутацію (дефолт `debug`) тест ловить.

## Що спитають на співбесіді — і що сказати

- **«Як MCP-сервер знає і користувача, і агента?»** «Runtime як внутрішній STS підписує короткий токен:
  `sub` — людина, `act` — агент, `aud` — один сервер, `run_id`, 5 хвилин. Токен людини далі не пересилаю —
  passthrough специфікація MCP забороняє. Стандартна альтернатива — Token Exchange (RFC 8693) у Keycloak.»
- **«Чому агент не може підтвердити перегляд сам?»** «Маршрут підтвердження довіряє лише IdP. Runtime може
  підписати будь-який делегований токен, але токен Keycloak — ні. Є тест: токен runtime з `sub=olena` і без
  `act` → 401.»
- **«Як доведете, що аудит не підробили?»** «Хеш-ланцюжок; `audit:verify` знаходить змінений або видалений
  рядок. Обрізаний хвіст — ні, для цього потрібен зовнішній якір. Запис — у транзакції `BEGIN IMMEDIATE`, інакше
  два сервіси роздвоїли б ланцюжок.»
- **«Що, якщо зламають runtime?»** «Він зможе діяти від імені тих, чиї токени має, і лише в межах `authorize`
  на серверах: ролі сервер бере зі свого довідника, а не з токена runtime. Підтвердити перегляд не зможе.»

## Вправи

Розв'язки: [04-security-solutions.md](04-security-solutions.md).

1. **(міні) Якір журналу.** `pnpm audit:anchor` друкує `seq` і hash останнього запису; `audit:verify --anchor
   <seq>:<hash>` падає, якщо такого рядка вже немає або hash інший. Тест: обрізаний хвіст тепер ловиться.
2. **(міні) Refresh токена людини.** Сесія чату довша за 30 хвилин → підтвердження з 401. Збережи
   `refresh_token` і оновлюй access token перед підтвердженням. Тест з рухомим годинником.
3. **(міні) `nbf` і `jti`.** Додай `jti` у делегований токен і пиши його в аудит. Навіщо `jti`, якщо токен і так живе 5 хвилин?
4. **(обговоримо) Варіант A.** Що зміниться, якщо замість власного STS використати Token Exchange (RFC 8693) у
   Keycloak? Хто тоді тримає ключ і що втратимо/виграємо?
5. **(обговоримо) Ролі в токені.** Що, якщо класти ролі людини в делегований токен і не дивитись у довідник на
   сервері? Що прискориться і що зламається при компрометації runtime?
6. **(живе) Keycloak.** Підніми Keycloak, пройди `pnpm chat --as ivan` і `--as bohdan`; вимкни Олену в адмінці —
   що станеться з її наступним входом і з уже виданим токеном?
