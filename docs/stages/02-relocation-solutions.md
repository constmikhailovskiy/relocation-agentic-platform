# Етап 2 (relocation) — розв'язки вправ з поясненнями

Вправи — у [02-relocation.md](02-relocation.md#вправи).

## Вправа 1. Нові критерії виводять з `needs_attention`

**Що хотіли (тест).** `set-criteria.test.ts`, «нові критерії виводять з needs_attention»:
- пошук у `needs_attention` після `set_criteria` → `searching`, в історії `{from, to, by, agent}`;
- в інших статусах статус не змінюється, історія порожня;
- `over_cap` у `needs_attention` — статус лишається (запис не відбувся — переходу теж немає).

До реалізації червоний був перший тест; два інші — запобіжники, зелені й до, і після.

**Як зроблено (`set-criteria.ts`).** Після `updateCriteria`: якщо статус `needs_attention` →
`assertTransition` → `store.changeStatus` з причиною «Нові критерії». Через `assertTransition`, а не напряму:
`TRANSITIONS` лишається єдиним джерелом правди, навіть коли перехід робить не `update_status`.

**Як переконалися.** Мутація `if (search.status === "needs_attention")` → `if (false)` → червоний тест.

**Схожий випадок, не зроблений:** `draft → searching` («критерії повні») за діаграмою теж мав би
спрацювати від `set_criteria`. У фікстурах немає пошуку в `draft`; якщо з'явиться — той самий прийом.

## Вправа 2. Термін дії запиту на перегляд

**Що хотіли (тест).** `request-viewing.test.ts`, «термін дії запиту на перегляд»:
- `expiresAt = now + 24 год`;
- підтвердження на мілісекунду пізніше → `expired`, статус пошуку не змінився;
- рівно в момент `expiresAt` — ще можна (межа з обох боків, як у вправі 5 listings);
- той самий запит після терміну створюється заново, а не повертає прострочений.

**Як зроблено (`request-viewing.ts`).**
- `VIEWING_TTL_MS` — константа; `expiresAt` рахується від `ctx.now()` (годинник сервера, не моделі).
- `confirmViewing`: `if (ctx.now() > approval.expiresAt)` → `expired` + подія аудиту `deny / expired`.
  ISO-рядки в UTC порівнюються як рядки, тому `>` працює без `Date`.
- Пошук наявного запиту ігнорує прострочені (`a.expiresAt >= now`). Без цього повтор вічно віддавав би
  мертвий запит — та сама пастка, що й з чужим запитом у рев'ю.
- Новий TypeScript: `Extract<Approval, { kind: "viewing" }>` — з union лишити варіанти, сумісні з `{ kind: "viewing" }`.

**Чому це важливо.** Користувач бачить «перегляд у суботу о 15:00» і підтверджує через три дні — слоти
вже в минулому або квартиру здали. Прострочене підтвердження — те саме, що підтвердження чогось іншого.

## Вправа 3. Ідемпотентний `notify_employee`

**Що хотіли (тест).**
- `notify-employee.test.ts`: той самий ключ → один лист і та сама відповідь; різні ключі або без ключа —
  кожен виклик надсилає; ключ прив'язаний до пошуку.
- `mcp.test.ts`: ключ іде в `_meta` запиту `tools/call`; у схемі інструмента його немає; повтор → один лист.

**Хто генерує ключ — модель чи runtime? Runtime.** Модель може забути ключ, повторити старий, вигадати
однаковий для різних листів — і все це «правдоподібно». Ключ має бути детермінованим від того, *що*
повторюється: `${run_id}:${step}` у runtime або ID activity в Temporal. Ретрай того самого кроку дає той самий
ключ, новий крок — новий.

**Як зроблено.**
- `notify-employee.ts`: `notifyEmployee(ctx, searchId, input, { idempotencyKey })` — ключ окремим параметром,
  не в `input` (який формує модель). Повтор повертає збережену відповідь до відправки.
- `store.ts`: `sentWithKey` / `rememberKey`, ключ `(searchId, key)`. У SQLite — таблиця з `PRIMARY KEY (search_id, key)`
  і запис у тій самій транзакції, що й лист в outbox.
- `mcp.ts`: другий аргумент обробника — `extra`; `extra._meta.idempotencyKey` кладе runtime. Модель `_meta` не формує.

**Як переконалися.** Мутація: прибрати `return previous` → червоні обидва тести (домен і MCP).

**Межа.** Ключ не перевіряє, що вміст повтору той самий. Повтор з тим самим ключем і іншим текстом поверне
відповідь першого виклику — так роблять і платіжні API (Stripe), але можна й відповідати помилкою.

## Вправа 4. Чи має `save_shortlist` перевіряти, що оголошення існує (обговорення)

**Варіанти.**
1. Довіряти ключу. Простота, `relocation` не залежить від `listings`.
2. Синхронно питати `listings` при `save_shortlist`. Точніше, але `relocation` падає разом з `listings`,
   з'являються таймаути й ретраї між сервісами, а дані все одно застаріють до перегляду.
3. Перевіряти там, де це справді важливо, — перед контактом з орендодавцем.

**Рекомендація: 1 + 3.** У `save_shortlist` — лише формат ключа (дешево, без мережі; можна додати
`regex(/^(olx|lun):/)`). Справжня перевірка — `check_availability` перед `request_viewing`: агент мусить її
викликати (це вже eval траєкторії в `case.md`), а runtime/Temporal перед відправкою запиту орендодавцю
(після `confirmViewing`) перевіряє ще раз. Шортлист — це чернетка для людини; помилка в ній дешева.
Контакт з орендодавцем — дорогий і незворотний; перевірка — там.

**Що сказати на співбесіді.** «Між сервісами я не роблю синхронних перевірок там, де помилка дешева: кожна
синхронна залежність множить відмови. Перевіряю там, де дія незворотна».

## Вправа 5. Optimistic locking (обговорення)

**Проблема.** Олена через агента і Тарас в UI одночасно міняють критерії: обидва прочитали версію 3, обидва
записали, переміг останній — зміни першого мовчки зникли («lost update»).

**Як додати.**
- У `Search` поле `version` (у `case.md` воно вже є в таблиці `searches`); `get_search` його повертає.
- `set_criteria` і `update_status` приймають необов'язковий `expected_version`. Запис:
  `UPDATE searches SET ..., version = version + 1 WHERE id = ? AND version = ?`; 0 змінених рядків → конфлікт.
- Помилка для моделі: `version_conflict`, `retryable: false`, текст «Пошук змінився з моменту читання.
  Виклич get_search, покажи користувачу зміни і повтори». Не `retryable: true`: сліпий повтор зі старими
  даними — це той самий lost update, лише відкладений.

**Чому `expected_version` необов'язковий.** `update_status` з `TRANSITIONS` уже частково захищений: перехід
перевіряється від поточного статусу. Обов'язкова версія зробила б кожен виклик залежним від свіжого
`get_search` — зайві кроки агента там, де конфлікт неможливий.

**Не зроблено в коді:** з'явиться разом із SQLite, де `WHERE version = ?` — природний механізм.

## Вправа 6. Мутаційна перевірка самостійно

Заміна `actor.sub === resource.ownerId` на `true` у `policy.ts` → **35 червоних тестів** у трьох шарах:
`policy.test.ts` (таблиця ролей), доменні тести інструментів (`get-search`, `set-criteria`, `save-shortlist`,
`update-status`, `budget-exception`, `notify-employee`) і MCP/HTTP (`mcp.test.ts`, `http.test.ts`).

Висновок: правило власника — найважливіший рядок `authorize`, і його стереже кожен шар. Якби впали лише
тести `policy.test.ts`, це означало б, що домен перевіряє права десь інакше (або не перевіряє).
