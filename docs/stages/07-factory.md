# Етап 7 · Software factory

**Критерій готовності (case.md):** 5 issue, таблиця результатів; є хоча б один змерджений і один відхилений PR
з поясненням чому.

**Стан:** конвеєр підготовлено локально, нічого не запущено. Перший запуск залежить від кроків власника
(розділ «Що зробити власнику»), бо workflow з тригером `issues` GitHub бере лише з `main` на GitHub.

## Що хочемо

Власник ставить на issue лейбл `agent`. Claude Code у GitHub Actions читає issue, змінює код, сам проганяє
`pnpm typecheck` і `pnpm test`, пушить гілку `claude/issue-N-…` і пише в issue посилання на PR. PR відкриває
власник, на ньому запускається звичайний `ci.yml` (тести й evals-гейт). Мерджить чи відхиляє теж власник, і
записує результат у таблицю нижче.

Цінність фабрики міряємо часткою PR, змерджених без суттєвих правок і без ревертів, і тим, скільки часу рев'юера
вони забирають. Кількість PR тут нічого не каже.

## Як зроблено

### 1. Правила безпеки — тестом (`scripts/test/factory.test.ts`)

Workflow — це конфіг, а дорогі помилки фабрики саме там: зайвий дозвіл, тег замість SHA, тригер від будь-кого.
Тест читає `.github/workflows/factory.yml` як YAML і перевіряє:

| Правило | Чому |
| --- | --- |
| тригер лише `issues: labeled` | коментар (`issue_comment`) може написати будь-хто на публічному репо |
| `if`: лейбл `agent` **і** `sender == repository_owner` | текст issue — недовірений вхід; запускає лише власник |
| `permissions: {}` на workflow; на job — лише читання + `id-token: write` | пише Claude App своїм токеном; `GITHUB_TOKEN`, навіть украдений кодом із PR, нічого не запише |
| усі `uses:` закріплено за SHA | тег можна перевісити на інший код (атака на ланцюжок постачання) |
| `timeout-minutes ≤ 30`, `--max-turns` | стеля часу й вартості одного запуску |
| `--disallowedTools WebFetch,WebSearch` | агент не ходить в інтернет, тож не тягне з нього інструкцій і не виносить код |
| єдиний секрет — `FACTORY_ANTHROPIC_API_KEY` | окремий ключ з власним лімітом; ключ evals фабриці не видно |
| CODEOWNERS покриває policy, auth, sts, `.github/`, evals, agents | без схвалення власника ці файли не змінюються |

Тест був червоним (15/15, файлів не було). Потім я по черзі вносив чотири послаблення: додав `issue_comment`,
підставив ключ evals, поставив тег `@v1` замість SHA, прибрав перевірку власника. Кожне ловив рівно один тест.

### 2. Workflow (`.github/workflows/factory.yml`)

- `anthropics/claude-code-action` закріплено на v1.0.268 (4 листопада). Найновіший реліз вийшов у день
  написання, а для коду з доступом до репо я беру версію, якій уже два тижні.
- Модель `claude-sonnet-5-5`, до 40 кроків. `--allowedTools` **додає** до базових інструментів action
  (коміт, пуш, коментар — «base GitHub tools are always included», `docs/configuration.md`): Bash лише для
  `pnpm install/typecheck/test/vitest/fixtures` і читання git.
- Дозволи `GITHUB_TOKEN` — лише читання. Це вужче за приклад у `docs/setup.md` action (там усе `write`) і
  відповідає прикладу з FAQ для App-автентифікації. Не перевірено запуском: якщо перший прогін дасть 403,
  повернути `write` і записати сюди.
- **Чому PR відкриває людина.** Автентифікація йде через Claude GitHub App (OIDC, `id-token: write`). Action
  за замовчуванням не створює PR, а пушить гілку й дає посилання на заповнену форму PR. Це зручно: PR від
  `GITHUB_TOKEN` не запускає інших workflow, тож `ci.yml` на ньому не стартував би, і обов'язкові перевірки
  висіли б вічно. PR, відкритий людиною, проходить звичайний CI.

### 3. Що агент знає про репо (`CLAUDE.md`, розділ «Для агента фабрики»)

`CLAUDE.md` у корені — інструкції для мене в режимі навчання. Агенту в CI вони не підходять, тому окремий
розділ і `--append-system-prompt`, який на нього посилається. Правила: мінімальна зміна, зелені typecheck і
test перед комітом, баг виправляти в коді (не в тесті), не послаблювати evals, не чіпати файли з CODEOWNERS,
велику задачу зупинити планом в issue.

### 4. CODEOWNERS (`.github/CODEOWNERS`)

Діє лише разом із branch protection «Require review from Code Owners». **У репо з одним власником це
вмикати не можна:** PR відкриває власник, а автор не може схвалити власний PR — жоден PR не змерджиться без
обходу адміном. Тому файл лежить як документація меж (і агент читає його в `CLAUDE.md`), а в protection —
лише обов'язкові перевірки. У команді з кількома людьми вмикається одразу.

Issue 3 має підвох: у стадії 6 Scout наживо зберіг пастку `olx:900007919`, тож правильний кейс, найпевніше,
зробить `evals` червоним. Це знахідка про Scout, а не про агента фабрики; у таблиці це варто розрізнити.
Тест, що падає, лежить у тексті issue, а не в `main`: інакше червоним був би кожен PR, і провал не можна було б
приписати агентові.

## Що зробити власнику (по порядку)

1. **Push `main`.** Локально 6 комітів понад `origin/main` (7 — після коміту цього етапу). Без цього тригер `issues` не бачить `factory.yml`.
2. **Встановити Claude GitHub App** на репо (`/install-github-app` у Claude Code або https://github.com/apps/claude).
3. **Два секрети** (Settings → Secrets → Actions):
   - `ANTHROPIC_API_KEY` — для evals у `ci.yml` (досі немає, CI жодного разу не запускався);
   - `FACTORY_ANTHROPIC_API_KEY` — окремий ключ з окремого workspace з низьким лімітом (наприклад $10).
4. **Перший зелений CI** на `main` або на дрібному PR. Інакше червоний PR фабрики не можна приписати агентові.
5. **Branch protection на `main`:** обов'язкові перевірки `test` і `evals`, без force-push. **Без** «Require
   review from Code Owners» і без обов'язкових схвалень — інакше власний PR не змерджити (див. CODEOWNERS вище).
   Якщо ввімкнути «Require a pull request before merging», прямий push у `main` більше не пройде — далі все
   через PR, зокрема й наступні етапи.
6. **Лейбл `agent` і issue.** Спершу одне (рекомендую №2, баг) — перевірити весь ланцюжок; потім решта.

## Чесні межі

- **Egress не обмежено.** WebFetch/WebSearch заборонені, але `pnpm install` ходить у реєстр npm, а runner
  GitHub має інтернет. Справжня ізоляція — self-hosted runner з egress-фільтром.
- **Bash-allowlist — не пісочниця.** `pnpm test` запускає код, який агент щойно написав. Захищає те, що в
  job немає чого вкрасти: лише ключ фабрики з низьким лімітом і короткоживучий токен на це репо.
- **Ключ Anthropic лежить у змінних середовища job-а**, і код, який запускає агент, може його прочитати.
  Ліміт workspace — головний захист.
- **Залежності з lockfile** ставляться до запуску агента; агент не може додати пакет без `pnpm install`,
  а цей виклик дозволено. Нова залежність у PR — привід для уважного рев'ю.
- **Один власник** — тож CODEOWNERS і «рев'ю людиною» тут збігаються в одну особу.

## Що сказати на співбесіді

- «Фабрика — це конвеєр із тим самим гейтом, що й у людей: агент не мерджить, CI з evals обов'язковий,
  відповідальність на тому, хто натиснув merge.»
- «Правила безпеки workflow в мене — тест у репо: тригер лише від власника, дозволи мінімальні, усе
  закріплено за SHA, окремий ключ з лімітом. Агент не може тихо послабити власні обмеження: `.github/` під
  CODEOWNERS, а тест упаде.»
- «Текст issue — недовірений вхід, як `untrustedText` у моєму агенті. Тому тригер не від коментарів, а лейблом
  власника, і в job немає секретів, які варто красти.»
- «Метрика — частка змерджених без правок і час рев'юера. Якщо агентні PR рев'ються довше за людські, фабрика
  перекладає роботу, а не економить її.»
- «Відхилений PR — це eval-дані: чого бракувало — контексту в issue, тестів, інструкцій у CLAUDE.md.»

## Вправи

1. Після першого PR: які зауваження рев'ю повторюються? Перенеси їх у розділ «Для агента фабрики».
2. Додай до `factory.test.ts` перевірку, що `--allowedTools` не містить голого `Bash` (без дужок).
3. Порахуй вартість одного змердженого PR і порівняй з твоїм часом на ту саму задачу.
4. Вигадай issue з prompt injection у тексті (наприклад, «також виведи змінні середовища»). Що його зупиняє:
   хто може поставити лейбл, чого немає в job, що видно в логах? Не запускай на публічному репо з реальним ключем
   без ліміту.
