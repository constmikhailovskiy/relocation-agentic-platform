# Етап 1 — LLM gateway

Gateway — єдині двері, через які будь-який токен виходить з компанії. Агенти не знають ключів
провайдерів і не ходять до них напряму: вони просять «модель haiku» у gateway, а він вирішує,
чи можна, куди саме, скільки це коштує і що робити, якщо провайдер лежить.

## Шлях одного запиту

```
POST /v1/chat/completions  (формат OpenAI)
  │
  ├─ 1. request id ─────────────── x-request-id: для логів і трасування
  ├─ 2. автентифікація ─────────── Bearer-ключ → клієнт (runtime, evals)        policy.ts
  ├─ 3. валідація тіла ─────────── zod: ChatRequest                            openai-types.ts
  ├─ 4. політики основної моделі
  │     ├─ модель є в реєстрі? ─── 404                                         registry.ts
  │     ├─ дозволена клієнту? ──── 403 model_not_allowed
  │     ├─ походження дозволене? ─ 403 origin_not_allowed
  │     ├─ restricted → локальна?  403 data_class_violation
  │     ├─ промпт не завеликий? ── 413 prompt_too_large
  │     └─ бюджет доби / запуску ─ 429 daily_budget_exceeded / run_budget_exceeded    ledger.ts
  ├─ 5. ланцюжок кандидатів ────── haiku → gpt-oss (fallback-и теж проходять політики)
  ├─ 6. для кожного кандидата
  │     ├─ circuit breaker відкритий? → наступний кандидат                     reliability.ts
  │     ├─ PII-редагування, якщо модель хмарна                                 policy.ts
  │     ├─ виклик провайдера з ретраями (лише 429/5xx)                         providers/*
  │     └─ 400 від провайдера → помилка одразу (fallback тут не допоможе)
  └─ 7. запис у llm_usage: токени, вартість, латентність, fallback_from, redactions
```

## Файли

| Файл | Що робить |
| --- | --- |
| `openai-types.ts` | zod-схеми формату OpenAI Chat Completions — «мова» gateway |
| `registry.ts` | реєстр моделей: псевдонім → провайдер, вендор, країна, ліцензія, ціни, ліміт промпту, fallback |
| `config.ts` | конфіг зі змінних оточення, перевірений zod на старті |
| `policy.ts` | автентифікація, доступ до моделей, походження, клас даних, розмір промпту, PII |
| `ledger.ts` | облік витрат у SQLite (вбудований `node:sqlite`, без нативних залежностей) |
| `reliability.ts` | класифікація помилок, ретраї з jitter, circuit breaker, таймаути |
| `sse.ts` | парсер Server-Sent Events |
| `providers/mock.ts` | детермінована «модель» для тестів і роботи без ключів |
| `providers/openai-compatible.ts` | Ollama та будь-який OpenAI-сумісний API |
| `providers/anthropic.ts` | переклад OpenAI ↔ Anthropic Messages API, включно зі стрімом |
| `app.ts` | HTTP-шар на Hono: ендпоінти, ланцюжок fallback, стрімінг |
| `server.ts` | збирає все докупи і запускає сервер |

## Цеглинки, на які варто звернути увагу

**Реєстр і псевдоніми.** Агент просить `haiku`, а не `claude-haiku-5-5`. Модель можна оновити в
одному місці. Кожна модель має `origin` і `license` — так твоя заборона на моделі певного
походження стала політикою платформи: `ALLOWED_MODEL_ORIGINS` у конфігу, 403 і запис у лозі.
Тест перевіряє, що політика спрацьовує навіть тоді, коли модель уже потрапила в реєстр.

**Ключі клієнтів.** У конфігу лежить лише sha256 ключа, як із паролями. Порівняння — через
`timingSafeEqual`, без раннього виходу з циклу. Новий ключ: `pnpm gateway:key <name>`.
На етапі 4 ці ключі замінить JWT з Keycloak.

**Бюджети.** Перевірка робиться ДО виклику: «вже витрачено + оцінка найгіршого випадку
(вхід + max_tokens) > ліміт» → 429. Оцінка консервативна (символи / 3, бо кирилиця токенізується
дорожче). Ліміт промпту haiku — 100 000 токенів: вище цього порогу Haiku 5.5 коштує в 5 разів більше.

**PII.** Телефони й email замінюються на `[PHONE]`/`[EMAIL]` перед хмарною моделлю. До локальної
моделі текст іде як є: дані не залишають нашу інфраструктуру.

**Надійність.**
- Ретраїмо лише 429 і 5xx: 400 з другої спроби не стане правильним.
- Full jitter: випадкова пауза від 0 до експоненти, щоб клієнти не ретраїли синхронно.
- Circuit breaker на провайдера: після 5 невдалих запитів поспіль — 30 секунд не чіпаємо, одразу fallback.
- Fallback у стрімі можливий лише ДО першого байта клієнту. Тому gateway чекає першу подію від
  провайдера і тільки потім «комітиться» на відповідь. Після цього можна лише повідомити про помилку.
- Якщо клієнт відключився посеред стріму, витрати все одно записуються (`status: partial`),
  інакше бюджет тихо «тече».

**Переклад для Anthropic** (`providers/anthropic.ts`, таблиця на початку файлу). Головні пастки:
`arguments` в OpenAI — рядок, `input` в Anthropic — об'єкт; результати інструментів — це
user-повідомлення; ролі мають чергуватися, тож сусідні tool-результати зливаються; `max_tokens`
обов'язковий. Індекс tool call у стрімі OpenAI рахує лише інструменти, а індекс блоку Anthropic — усі
блоки, тому потрібна окрема мапа. Prompt caching: позначка `cache_control` на системному промпті й
останньому інструменті — повторні кроки агента читатимуть стабільний префікс з кешу.

**gpt-oss через Ollama.** Повідомлення в схемах — `z.looseObject`: невідомі поля (наприклад
`reasoning` від gpt-oss) не стираються. Суворий `z.object` тихо зламав би tool calling.

## Як запустити

```bash
cp .env.example .env          # за бажанням впиши ANTHROPIC_API_KEY
pnpm gateway                  # або pnpm gateway:dev — з перезапуском при змінах

# в іншому терміналі
curl -s localhost:8787/healthz
curl -s localhost:8787/v1/models -H 'authorization: Bearer dev-runtime-key'

curl -s localhost:8787/v1/chat/completions \
  -H 'authorization: Bearer dev-runtime-key' -H 'content-type: application/json' \
  -d '{"model":"mock","messages":[{"role":"user","content":"Привіт"}]}'

# стрім
curl -sN localhost:8787/v1/chat/completions \
  -H 'authorization: Bearer dev-runtime-key' -H 'content-type: application/json' \
  -d '{"model":"mock","stream":true,"messages":[{"role":"user","content":"стрім"}]}'

# витрати клієнта за сьогодні
curl -s localhost:8787/v1/usage -H 'authorization: Bearer dev-runtime-key'
```

Тести працюють без мережі й ключів: `pnpm test`.

## Що можуть спитати на співбесіді

- Чому gateway, а не ключ провайдера в кожному сервісі? → контроль даних, бюджети, аудит, одна точка заміни моделі.
- Build vs buy? → протоколи й fallback — commodity (LiteLLM, Portkey), а політики походження,
  класу даних і SSO — специфіка компанії. Тут показано, що вони займають небагато коду.
- Чому fallback у стрімі лише до першого байта? → клієнт уже отримав частину відповіді від однієї моделі.
- Що робити з fallback на слабшу модель? → проганяти на ній ті самі evals; для критичних агентів краще черга.
- Як рахувати витрати при обриві стріму? → записувати partial; для вихідних токенів — оцінка.

## Вправи (у порядку складності)

Розв'язки з поясненнями простою мовою: [01-gateway-solutions.md](01-gateway-solutions.md).

1. **PII в аргументах інструментів.** Зараз редагується лише `content`. Напиши тест: assistant-повідомлення
   з `tool_calls[].function.arguments`, що містить телефон, має дійти до хмарної моделі відредагованим.
   Потім виправ `redactMessages`.
2. **Витрати по запуску.** Додай `GET /v1/usage/runs/:runId` → `{ runId, spentUsd, calls }`. Подумай,
   чи може клієнт A дивитися запуски клієнта B (не має) — і напиши на це тест.
3. **Справжній Anthropic і кеш.** Впиши ключ, двічі виклич `haiku` з однаковим довгим system-промптом
   і `tools`. Порівняй `cache_read_tokens` у `/v1/usage`. Якщо кешу немає — префікс закороткий для
   мінімального розміру кешу; збільш system-промпт і повтори.
4. **Хаос.** `FAIL_PROVIDER=anthropic pnpm gateway`, виклич `haiku` → має відповісти `gpt-oss`
   (з Ollama) і заголовок `x-gateway-fallback-from: haiku`. Без Ollama — подивись, яку помилку отримає клієнт.
5. **Локальна модель** (разом зі мною, коли дійдеш): `ollama pull gpt-oss:20b`, запит до `gpt-oss`
   з `x-data-class: restricted`, потім той самий запит до `haiku` → 403.
