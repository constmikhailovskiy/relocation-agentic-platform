# Етап 2 — розв'язки вправ з поясненнями

## Вправа 1. Адаптер ЛУН

**Що хотіли (тест).** `mcp/listings/test/lun.test.ts` — 5 тестів: усі 32 записи стають валідним `Listing`,
перший запис розкладено поле за полем, ціни в доларах переведено за курсом, без ціни — `AdapterError`,
невідомий район — `AdapterError` з ключем запису. До реалізації — 5 червоних.

**Крок 0: спершу рефакторинг.** Хелпери `parseAmenities`, `toUah` і типи `AdapterOptions`, `Adapted`
лежали в `olx.ts`. Якби `lun.ts` імпортував їх звідти, ЛУН залежав би від OLX — дивна залежність між
рівноправними адаптерами. Тому все спільне переїхало в `adapters/common.ts`, туди ж — новий `finalize`:

```ts
export function finalize(key: string, candidate: unknown, contact: { name: string; phone: string }): Adapted {
  const parsed = Listing.safeParse(candidate);
  if (!parsed.success) throw new AdapterError(key, `не відповідає схемі Listing: ...`);
  return { listing: parsed.data, contact: { listingKey: key, ...contact } };
}
```

Тепер «останній бар'єр» (перевірка схемою) — одна функція для всіх адаптерів, і новий адаптер не
може «забути» його. Перевірка рефакторингу: 7 тестів OLX лишились зеленими *до* того, як я почав ЛУН.

**Як зроблено (`adapters/lun.ts`).** Різниця з OLX — лише у форматі сирих полів:

| Поле ЛУН | Проблема | Розв'язок |
| --- | --- | --- |
| `district_name: "Шевченківський район"` | зайве слово «район» | `districtFromUk` уже його відкидає; невідомий → `fail` |
| `price_uah` / `price_usd` | ціна в одному з двох полів, обидва можуть бути `null` | гривня пріоритетна; обидва `null` → `AdapterError` |
| `floor: "1/10"` | два числа в одному рядку | `split("/").map(Number)` → `[1, 10]` |
| `features: ["балкон", ...]` | уже масив | `parseAmenities` без `split` |
| `pets_ok: boolean \| null` | уже наш формат | передаємо як є |
| `owner.tel` | інша назва поля | `{ name, phone: raw.owner.tel }` у `finalize` |

**Синтаксис, який з'явився вперше:**

- **Ланцюжок тернарних операторів** для ціни:
  ```ts
  const price: Money =
    raw.price_uah !== null ? { amount: raw.price_uah, currency: "UAH" }
    : raw.price_usd !== null ? { amount: raw.price_usd, currency: "USD" }
    : fail("немає ні ціни в гривнях, ні в доларах");
  ```
  Читається як `if / else if / else`. Остання гілка має тип `never` (вона кидає помилку), тому
  TypeScript погоджується, що `price` — завжди `Money`. Анотація `: Money` потрібна, щоб `"UAH"` був
  літералом валюти, а не просто `string`.
- **Деструктуризація масиву:** `const [floor, totalFloors] = "1/10".split("/").map(Number)` — перший
  елемент у `floor`, другий у `totalFloors`.
- **`noUncheckedIndexedAccess` у дії.** TypeScript не знає, скільки елементів поверне `split`, тому
  `floor` має тип `number | undefined`. Звідси `floor ?? fail(...)`: якщо елемента немає — помилка з ключем.
  А якщо елемент є, але не число (`"1/x"` → `NaN`), його зловить `finalize`: `Listing` вимагає ціле число.
- **Spread в об'єкті:** `{ listingKey: key, ...contact }` — нове поле плюс усі поля `contact`.

**Чому гривня пріоритетна, якщо заповнено обидва поля.** У фікстурах такого немає, але в житті буває.
Гривня — ціна, яку назвав власник; долари в такому разі — довідковий перерахунок сайту за його курсом.
Перераховувати назад за нашим курсом означало б отримати іншу суму, ніж бачить людина на сайті.

**Як переконатися самому.** `pnpm vitest run mcp/listings` → 12 тестів зелені. Спробуй поміняти
місцями гілки гривні й долара в тернарному операторі: тести поки не впадуть, бо у фікстурах немає
записів з обома цінами. Це прогалина, яку закриває ще один тест — хороша міні-вправа.

**Що сказати на співбесіді.** «Кожне джерело має свій адаптер, який знає лише свій сирий формат,
а спільні правила — розбір зручностей, валюта, перевірка схемою — в одному модулі. Тому новий
постачальник даних — це новий адаптер і набір тестів на його фікстурах, а решта системи не змінюється.
Битий запис дає типізовану помилку з ключем, а не сміття, яке вибухне далеко від причини».

## Вправа 2. Дедуплікація

**Що хотіли (тест).** `mcp/listings/test/dedupe.test.ts` — 6 тестів, ключ відповідей — `traps.duplicates`:

| Тест | Навіщо |
| --- | --- |
| 80 → 70 | головна арифметика: 48 + 32 − 10 |
| усі 10 пар злились, ЛУН став псевдонімом OLX | кожна пара з ключа відповідей, а не лише кількість |
| ЛУН першим на вході — однаково лишається OLX | результат не залежить від порядку |
| ціна відрізняється на 500 — однаково злились | ціна не входить у відбиток |
| інший поверх — дві квартири | захист від хибного злиття |
| пробіли й регістр у вулиці — злились | нормалізація тексту |

До реалізації — 6 червоних.

**Перш ніж писати код — подивились у дані.** В усіх 10 парах OLX опубліковано раніше (генератор так і
задумав: ЛУН агрегує оголошення, дубль з'являється пізніше). А відбиток «район + вулиця + кімнати +
площа + поверх» збігається рівно в 10 групах по 2 — отже, хибних злиттів на фікстурах немає.

**Як зроблено (`mcp/listings/src/dedupe.ts`).**

1. **Відбиток** (`fingerprint`) — те, що не змінюється між сайтами: район, нормалізована вулиця,
   кімнати, площа, поверх. Ціни немає навмисно.
2. **Прохід 1:** `Map<відбиток, переможець>`. Для кожного запису: якщо переможця ще немає або цей
   запис опубліковано раніше — він новий переможець.
3. **Прохід 2:** кожен, хто не переміг, записується в `aliasOf: ключ дубля → ключ переможця`.

**Чому лишаємо ранішу копію і зберігаємо псевдоніми.** Рання копія — оригінал; агрегатор її повторює.
Але й ключ дубля не можна просто викинути: агент міг отримати `lun:...` раніше (з кешу, з шортлиста, від
користувача), і `get_listing` / `check_availability` мають працювати й для нього. Тому `aliasOf`.

**Чому однаковий час розв'язується ключем.** Без цього правила переможець залежав би від порядку на
вході, а порядок — від того, яке джерело відповіло першим. Нестабільний результат = нестабільні evals.

**Синтаксис:**

- `new Map<string, Listing>()` — **generic**: у кутових дужках кажемо, які типи ключів і значень.
  Тепер `winners.get(fp)` має тип `Listing | undefined`, і TypeScript змусить перевірити `undefined`.
- `[...winners.values()]` — spread ітератора в масив. `Map` пам'ятає порядок вставки, тож результат стабільний.
- `Date.parse(...)` замість порівняння рядків: надійніше, якщо джерела форматують час по-різному.

**Що свідомо НЕ зроблено.** Ціна переможця лишається як є, навіть якщо на ЛУН вона на 500 грн вища.
Чи показувати користувачеві «на іншому сайті дорожче» — продуктове питання; у генераторі ці пари
позначені як майбутня задача для software factory.

**Що сказати на співбесіді.** «Дедуплікація — це відбиток із полів, стабільних між джерелами, без
ціни. Переможець визначається детерміновано, а ключі дублів не зникають — вони стають псевдонімами,
щоб посилання, які агент уже бачив, продовжували працювати. Перевіряю на фікстурах з відомими парами
і окремим тестом на хибне злиття».

## Вправа 3. Каталог і політика битих записів

**Що хотіли (тест).** `mcp/listings/test/catalog.test.ts` — 5 тестів:

| Тест | Що перевіряє |
| --- | --- |
| чисті фікстури → 70 квартир, 10 псевдонімів, 0 пропущених | агрегатор правильно склеює адаптери й дедуплікацію |
| у кожної квартири є контакт в окремій мапі | контакти доступні серверу, але не лежать у `Listing` |
| невідомий район в одному з 80 → 69, причина в `skipped` | `AdapterError` пропускається й записується |
| ЛУН із `floor: "третій"` → `lun:#0` у `skipped` | сирий запис не тієї форми теж пропускається |
| адаптер кидає `TypeError` → каталог падає | баг у нашому коді не ховається в лічильнику |

До реалізації — 5 червоних.

**Політика: три види помилок — три реакції.**

| Що сталося | Чия провина | Реакція |
| --- | --- | --- |
| запис не проходить схему джерела (`OlxRaw` / `LunRaw`) | джерело | пропустити; ключ `<source>:#<номер>`, бо `id` теж може бути битим |
| форма правильна, але дані безглузді → `AdapterError` | джерело | пропустити; ключ запису й причина |
| будь-яка інша помилка (`TypeError`, ...) | **ми** | пробросити: каталог падає |

Чому не «ловити все»? Якщо ловити всі помилки, баг в адаптері (скажімо, звернення до поля, якого
немає) тихо перетвориться на «пропущено 48 записів з 48» — і пошук просто стане порожнім, без жодного
сигналу. Падіння голосне; порожній результат — ні.

**Як зроблено (`mcp/listings/src/catalog.ts`).**

- Вхід — `unknown[]`, а не `OlxRaw[]`: це зовнішні дані, довіряти їхній формі не можна. Перша
  перевірка — сира схема джерела (`schema.safeParse`), друга — адаптер з `finalize`.
- `adaptAll<Raw>(source, records, schema, adapt, ...)` — одна функція для обох джерел.
- Адаптери передаються параметром (`adapters = DEFAULT_ADAPTERS`), тож тест підставляє «зламаний»
  адаптер і перевіряє, що помилка не ховається. Це **впровадження залежності** (dependency injection)
  у найпростішій формі — параметр зі значенням за замовчуванням.
- Контакти зберігаються лише для квартир, що лишились після дедуплікації.

**Синтаксис, який з'явився вперше:**

- **Generic-функція** `function adaptAll<Raw>(..., schema: z.ZodType<Raw>, adapt: (raw: Raw, ...) => Adapted)`.
  `Raw` — «змінна для типу». Коли передаємо `OlxRaw`-схему, TypeScript сам виводить `Raw = OlxRaw` і
  перевіряє, що `adapt` приймає саме `OlxRaw`. Передати схему ЛУН з адаптером OLX не вийде — помилка компіляції.
- **`e instanceof AdapterError`** — звуження типу в `catch`: там `e` має тип `unknown`, а після перевірки
  TypeScript знає, що це `AdapterError` з полями `key` і `reason`.
- **`type Skipped = Catalog["skipped"]`** — тип поля іншого типу, щоб не описувати його двічі.
- **`import type { z }`** — імпорт лише для типів: у зібраному JavaScript його не буде.

**Чого свідомо ще немає.** Порогу тривоги: якщо пропущено, скажімо, понад 20% записів джерела, це вже не
«кілька битих оголошень», а інцидент (джерело змінило формат). Це метрика й алерт на рівні сервера —
повернемось на етапі прод/on-call.

**Що сказати на співбесіді.** «Я розрізняю три види помилок: не та форма від джерела, безглузді дані від
джерела і баг у моєму коді. Перші два — пропустити, записати причину, порахувати в метриці. Третій —
падати голосно. Інакше баг виглядає як "сьогодні мало оголошень", і його ніхто не помітить».

## Вправа 4. Обидві ціни в ЛУН

**Що хотіли (тест).** `lun.test.ts`, «Адаптер ЛУН: обидві ціни заповнено»: запис з `price_uah: 15000` і
`price_usd: 400` → `price = { amount: 15000, currency: "UAH" }`, `priceUah = 15000`.

**Як переконалися.** Це тест-характеристика: код уже був, тож тест зелений одразу. Його цінність доводить
мутація: переставили гілки тернарного оператора в `adapters/lun.ts:16-19` (долар перед гривнею) → тест
червоний. Важливо: **до** цього тесту ця мутація проходила непоміченою — жоден старий тест не падав.
У фікстурах немає записів з обома цінами, тож тест закрив справжню дірку, а не продублював наявний.

## Вправа 6. Стеля `limit`

**Що хотіли (тест).** `mcp.test.ts`: `limit: 51` → `isError`; `limit: 50` — можна (обидві сторони межі).

**Чому стеля потрібна, якщо пошук локальний.** Кожен рядок результату — це токени в контексті моделі:
гроші, затримка і «шум», у якому модель гірше знаходить головне. Плюс обмеження шкоди: модель, яку
injection переконав «покажи все», не витягне весь каталог одним викликом.

**Як переконалися.** Прибрали `.max(MAX_LIMIT)` у `mcp.ts` → тест на 51 червоний.

## Вправа 7. Хто маскує телефон в описі (обговорення)

**Варіанти.**

| | Лише gateway (як зараз) | Ще й listings вирізає телефон орендодавця |
| --- | --- | --- |
| Що ловить | будь-який номер за шаблоном | саме той номер, який сервер знає з `contact` |
| Слабке місце | номер у незвичному форматі («нуль шість сім…») | номер у іншому форматі, ніж у `contact`, — потрібна нормалізація цифр |
| Принцип | одна сітка на виході до провайдера | мінімізація даних біля джерела (як з полем `contact`) |

**Рекомендація: два шари.** listings уже вирішив не віддавати контакти моделі — було б непослідовно віддавати
той самий телефон, якщо орендодавець вписав його в опис. Вирізати варто за нормалізованими цифрами
(`replace(/\D/g, "")`, порівнювати останні 9 цифр), замінюючи на `[PHONE]`. Gateway лишається загальною сіткою:
він ловить номери, яких listings не знає (чужі, другий номер орендодавця).

**Що станеться з пасткою `phoneInText`.** Вона перестане доходити до gateway, тож тест PII-фільтра gateway
на ній більше не можна будувати — йому потрібен власний синтетичний вхід з номером (він і так кращий:
не залежить від фікстур). У `mcp/listings/test/mcp.test.ts:168-170` виняток для `phoneInText` треба
прибрати: телефон не має бути в жодному полі.

**Не зроблено в коді свідомо:** це рішення про архітектуру захисту — за тобою. Якщо береш, порядок такий:
спершу змінити тест у рядках 168-170 (червоний), потім реалізація в `finalize` (`adapters/common.ts`).
