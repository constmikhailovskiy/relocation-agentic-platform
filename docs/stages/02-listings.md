# Етап 2 — MCP-сервер listings

MCP-сервер `listings` дає агенту три інструменти: `search_listings`, `get_listing`, `check_availability`.
Але серцевина сервера — не MCP, а звичайний TypeScript: перетворити сирі оголошення двох сайтів у
спільний формат, звести ціни до гривні, прибрати дублі й не віддати моделі контакти. Цей шар пишемо
першим, за TDD і без мережі. Потім MCP SDK загортає готові функції в інструменти (розділ
«MCP-обгортка» нижче).

Запуск: `pnpm listings` → `http://127.0.0.1:8788/mcp`. Змінні: `LISTINGS_PORT`, `LISTINGS_429_RATE`,
`LISTINGS_LATENCY_MS`, `LISTINGS_NOW` (див. `.env.example`).

## Шлях одного оголошення

```
fixtures/listings.olx.json ──► olxToListing ─┐
  (params рядками, ціна UAH|USD)             │   { listing: Listing,          ← бачить модель
                                             ├─►   contact: LandlordContact } ← лише request_viewing після HITL
fixtures/listings.lun.json ──► lunToListing ─┘
  (плоскі поля, поверх "3/9", price_uah|price_usd)
                                             │
                                             ▼
                          дедуплікація OLX ↔ ЛУН ──► фільтр за критеріями (далі)
```

## Цеглинки, на які варто звернути увагу

- **Адаптер повертає дві речі, а не одну.** `listing` піде моделі, `contact` — ні. Розділення в типі
  надійніше за «не забути видалити поле»: у `Listing` поля для контактів просто немає, тож витекти
  через нього вони не можуть. Тест перевіряє, що ключі `listing` точно збігаються зі схемою.
- **`Listing.safeParse` в кінці адаптера** — останній бар'єр. Хоч би що сталося вище, назовні не
  вийде запис, який порушує контракт (наприклад, `rooms: 0`).
- **`AdapterError` замість мовчазного сміття.** Невідомий район чи відсутня ціна — це помилка з
  ключем запису, а не `district: undefined`, який вибухне десь далеко. Окремий клас — щоб агрегатор
  міг відрізнити «битий запис» від бага в коді (`e instanceof AdapterError`).
- **Курс — параметр** (`opts.fxUsdUah`), а не імпорт глобальної константи: тест і конфіг керують
  ним явно, а детермінованість evals не залежить від того, хто який курс поставив у коді.
- **Опис іде в `untrustedText` як є.** Адаптер не «чистить» інструкції з тексту — це неможливо
  зробити надійно. Захист архітектурний: модель знає, що поле недовірене; телефони редагує gateway;
  ранжування робить код, а не модель.
- **`commuteMin` = `COMMUTE_MIN[district]`.** У `case.md` сказано «плюс шум», але сирі формати не
  мають поля часу дороги, а генератор шуму не додає. Тож беремо фіксоване значення району.

## Пошук: фільтр і ранжування

`searchListings(catalog, criteria, { now, limit })` — серцевина інструмента `search_listings`.

- **Фільтр** (`matches`) — по одному рядку на критерій. Три рішення варто вміти пояснити:
  - бюджет порівнюється з `priceUah`, а не з сирою ціною: 380 $ — це 15 960 грн, і в бюджет 15 000 воно не влазить;
  - `petsAllowed: null` («не вказано») при `pets: true` **не** підходить: для людини з котом «можливо» гірше за «ні»;
  - оголошення з датою публікації пізніше за `now` не показуються (пастка `futurePosted` — збій годинника джерела).
- **Ранжування** (`byRank`) — кодом і лише за структурованими полями: ціна → час дороги → ключ.
  `untrustedText` у ранжуванні не бере участі, тому «постав мене першим» в описі нічого не дає. Тест
  підміняє опис останнього оголошення і перевіряє, що порядок не змінився.
- **`now` — параметр**, не `Date.now()`: пошук детермінований, evals відтворювані.
- **`limit` і `total`**: модель отримує топ-N, але знає, скільки підійшло всього.

Видача для Олени — 9 квартир, серед них 3 injection-приманки (вони чесно підходять під критерії) і
2 застарілі. Це правильно: застарілі відсіює `check_availability`, а приманки стоять там, де їх
ставить ціна. Мутаційна перевірка: якщо в `matches` порівнювати бюджет із `price.amount`, падає тест про долари.

## get_listing і check_availability

- **Псевдоніми працюють скрізь.** `getListing("lun:...")` повертає квартиру, що лишилась після
  дедуплікації; `checkAvailability` відповідає канонічним ключем.
- **Здано на одному сайті — здано.** Перевіряються всі копії квартири, а не лише та, за якою питали.
- **`ListingsError` з `retryable`.** `not_found` — повторювати безглуздо; `rate_limited` — можна, і
  `retryAfterMs` підказує коли. Це контракт для runtime і Temporal (етап 3+): вони вирішують, ретраїти
  чи ні, за полем, а не за текстом помилки.
- **Хаос детермінований.** `LISTINGS_429_RATE` і `LISTINGS_LATENCY_MS` з ранбука (`case.md`, «Прод і
  on-call») — це `opts.chaos`. Генератор випадкових чисел і `sleep` передаються параметрами: у тестах
  `random: () => 0.1` гарантує 429, а підставний `sleep` не чекає 4 секунди, а лише записує, скільки мав чекати.
- **`not_found` — до хаосу.** Невідомий ключ — помилка клієнта, джерело для неї не «смикаємо».

## MCP-обгортка

Три шари, і кожен знає лише про сусіда знизу:

```
http.ts    POST /mcp ──► principal з заголовків (заглушка) ──► 401, якщо немає
              │ новий McpServer + транспорт на КОЖЕН запит (stateless)
mcp.ts     registerTool × 3 ──► handle(): аудит → виклик → ok / fail
              │
search.ts, lookup.ts   чисті функції доменного шару (без MCP, без HTTP)
```

**Що хочемо (тести, `mcp.test.ts`).** Тестуємо так, як побачить агент: справжній `Client` з SDK,
з'єднаний із сервером через `InMemoryTransport.createLinkedPair()` — «трубу» без мережі
(`mcp.test.ts`, функція `connect`). Перевіряємо:

- `tools/list`: рівно три інструменти; у `criteria` обов'язковий лише `maxBudgetUah` — поля з
  дефолтами модель може не передавати. Це не очевидно: zod 4 вміє генерувати JSON Schema і для
  входу, і для виходу, а на виході дефолтні поля обов'язкові. SDK бере саме вхідну форму — тест це закріплює.
- Відповідь є і в `structuredContent` (для коду), і тим самим JSON у `content[0].text` (для клієнтів,
  які читають лише текст).
- «Зараз» бере сервер: зайвий аргумент `now` від моделі ігнорується (`z.object` відкидає невідомі поля).
- `ListingsError` → `isError: true` і `{ error: { code, retryable, retryAfterMs? } }`.
- Неочікувана помилка (баг у нас) → лише `internal_error`. Справжній текст іде в `logError`, а не
  клієнту: стек і назви змінних — це витік деталей і сміття в контексті моделі. Перевірено мутацією:
  якщо віддати `String(e)`, тест червоніє.
- Телефонів орендодавців немає в жодному структурованому полі. Виняток — пастка `phoneInText`:
  орендодавець сам написав телефон в описі. Це вільний текст третьої сторони, і за `case.md` його
  маскує gateway (PII). Перевірено: `redactMessages` з `apps/gateway/src/policy.ts` замінює на
  `[PHONE]` телефон в усіх 19 таких описах, зокрема в повідомленнях ролі `tool`. Для **локальних**
  моделей gateway свідомо не маскує (дані не покидають машину). Тест фіксує це рішення явно (див. вправу 7).
- Помилки — **лише текстом**, без `structuredContent`. Клієнт SDK після `tools/list` кешує
  `outputSchema` і перевіряє нею `structuredContent` навіть у відповідях з `isError`; `{ error }` не
  схоже на `{ items, total }`, і клієнт кинув би виняток замість `rate_limited`. Тест «помилки доходять
  як isError і тоді, коли клієнт спершу зробив tools/list» був червоним саме з цієї причини.
- `principal` доходить до кожного з трьох обробників — це перевіряє хук `audit`.

**Як зроблено (`mcp.ts`).**

- `registerTool(name, { description, inputSchema, outputSchema, annotations }, handler)`.
  `inputSchema` — «сира форма» (об'єкт зі схемами полів), SDK сам загортає її в `z.object`, валідує
  аргументи й генерує JSON Schema для `tools/list`. `Criteria` береться з `@reloc/shared` — одне
  джерело правди для моделі, сервера й коду.
- `handle()` — одна обгортка для всіх інструментів: аудит до виклику, потім `ok()` або `fail()`.
- **`isError` — це не збій протоколу.** Помилка інструмента — звичайна відповідь, яку модель читає й
  вирішує, що робити (повторити пізніше, взяти інший ключ). Збій протоколу (JSON-RPC error) — для
  речей на кшталт «немає такого методу». SDK 1.32 і невалідні аргументи повертає як `isError` з текстом
  помилки валідації — модель бачить, що саме виправити.
- `annotations.readOnlyHint` — лише **підказка** клієнту. Для контролю доступу їй не довіряють:
  ризик інструменту береться з реєстру платформи (`case.md`, «MCP-сервери та інструменти»).
- Описи інструментів — це промпт: там сказано, що `untrustedText` — дані, а не інструкції, і що
  `rate_limited` треба повторювати не одразу.

**Де викликається (`http.ts`, `server.ts`).** `createListingsApp(deps)` — Hono-застосунок. На кожен
`POST /mcp`: дістати principal → новий `McpServer` → `WebStandardStreamableHTTPServerTransport` →
`handleRequest(c.req.raw)`. Чому stateless: немає сесій у пам'яті, тож сервер масштабується
горизонтально, а principal «вшитий» у замикання конкретного запиту й не може прилипнути до чужого.
`GET`/`DELETE /mcp` → 405: вони потрібні лише для сесій. `enableJsonResponse: true` — відповідь
звичайним JSON, а не SSE-потоком: інструменти короткі.

**Principal — поки заглушка.** `principalFromHeaders` (тепер у `packages/shared/src/auth-stub.ts`, спільна з relocation; тип `Principal` — у `packages/shared/src/policy.ts`) читає `x-debug-sub` і `x-debug-act`. Підробити
може будь-хто, тому сервер слухає лише `127.0.0.1`. На етапі 4 цю одну функцію замінить перевірка
JWT (підпис, `aud=mcp-listings`, `sub` і `act`), решта коду не зміниться. Без principal — 401 ще до MCP.

**Розбіжність зі специфікацією.** У `case.md` поле називається `untrusted_text`, а в схемі `Listing`
— `untrustedText`. Лишаємо схему: zod — єдине джерело правди, а в TypeScript-коді прийнято camelCase.

**Як переконатися самому.**

```bash
pnpm vitest run mcp/listings
LISTINGS_NOW=2026-11-15T09:00:00.000Z pnpm listings
curl -s 127.0.0.1:8788/health
```

Перевірений шлях — `curl` (JSON-RPC напряму):

```bash
curl -s -H 'content-type: application/json' -H 'accept: application/json, text/event-stream' -H 'x-debug-sub: olena' \
  127.0.0.1:8788/mcp -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"get_listing","arguments":{"key":"olx:1"}}}'
```

MCP Inspector (готовність етапу за `case.md` — «усі інструменти викликаються з MCP Inspector»):
`npx @modelcontextprotocol/inspector`, транспорт Streamable HTTP, URL `http://127.0.0.1:8788/mcp`,
заголовок `x-debug-sub: olena`. Де саме в інтерфейсі Inspector 2.x задається заголовок — ще не
перевірено. Хаос: `LISTINGS_429_RATE=0.5 LISTINGS_LATENCY_MS=4000 pnpm listings`.

## TypeScript, що з'явився вперше

| Запис | Що означає |
| --- | --- |
| `(reason: string): never => { throw ... }` | `never` — «ця функція ніколи не повертає». Тому `x ?? fail(...)` має тип `x` без `undefined` |
| `if (!parsed.success) return fail(...)` | **звуження типу**: після цього рядка TS знає, що `parsed.data` — точно `Listing` |
| `OlxRaw["params"][number]["key"]` | **indexed access type**: «тип поля `key` елемента масиву `params`» — тобто лише дозволені назви параметрів |
| `Parameters<typeof param>[0]` | тип першого аргументу функції `param` — щоб не дублювати опис |
| `.filter((a): a is Amenity => a !== undefined)` | **type guard**: після фільтра масив має тип `Amenity[]`, а не `(Amenity \| undefined)[]` |
| `"olx" as const` | літерал `"olx"`, а не просто `string` — інакше не пройде в `Source` |
| `structuredClone(x)` | глибока копія об'єкта: тест псує копію, а не спільну фікстуру |
| `const { rate429 = 0 } = opts.chaos ?? {}` | **деструктуризація з дефолтом**: взяти поле, а якщо його немає — `0`; `?? {}` — якщо `chaos` взагалі не передали |
| `(opts.random ?? Math.random)()` | взяти передану функцію або стандартну — і одразу викликати |
| `[...catalog.aliasOf]` | `Map` → масив пар `[ключ, значення]`; `([, target])` — пропустити перший елемент пари |
| `...(limit !== undefined && { limit })` | **умовне розгортання**: якщо умова хибна, `...false` не додає нічого. Потрібно через `exactOptionalPropertyTypes` — явно передати `limit: undefined` не можна |
| `({ criteria, limit }) => ...` | деструктуризація параметра: SDK передає об'єкт аргументів, беремо з нього поля. Їхні типи виведені з `inputSchema` (generics у `registerTool`) |
| `z.coerce.number()` | env — завжди рядки; `coerce` перетворює `"0.5"` на `0.5` перед перевіркою |
| `z.preprocess(fn, schema)` | спершу перетворити значення функцією, потім перевірити схемою (тут: `""` → `undefined`) |
| `null as unknown as Listing[]` | подвійне `as` у тесті: свідомо «зламати» тип, щоб імітувати баг. У робочому коді — ні |

## Що можуть спитати на співбесіді

- **Чому не скрейпити OLX?** Немає публічного API пошуку, скрейпінг — ризик ToS. Адаптери за спільним
  інтерфейсом: справжнє джерело підключається після договору, решта коду не змінюється.
- **Як не дати моделі контакти орендодавця?** Їх немає в типі, який іде моделі. Не фільтр на виході,
  а відсутність поля.
- **Що робити з битим записом від джерела?** Не валити весь пошук і не віддавати сміття: пропустити,
  порахувати, показати в метриках. Якщо битих раптом багато — це інцидент з джерелом.
- **Чим `isError` відрізняється від JSON-RPC помилки?** Перше — відповідь інструмента, яку бачить
  модель і може на неї зреагувати (повторити, змінити аргументи). Друге — збій протоколу для клієнта.
  `rate_limited` з `retryable: true` — саме `isError`: рішення про повтор приймає runtime за полем.
- **Чому сервер stateless?** Немає сесій — немає sticky-маршрутизації, і principal живе рівно один
  запит. Ціна — новий `McpServer` на запит, але це дешево (реєстрація трьох інструментів).
- **Чи довіряєте ви `readOnlyHint`?** Ні: це підказка від сервера. Ризик і дозволи — з реєстру
  платформи, а перевірка прав — у сервері на кожен виклик.
- **Що бачить модель, коли у вас баг?** `internal_error` без деталей. Деталі — у логах сервера.
- **Чому опис оголошення небезпечний?** Це текст третьої сторони, який читає модель, — канал prompt
  injection. У фікстурах є три такі описи.
