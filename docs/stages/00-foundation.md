# Етап 0 — фундамент

Мета етапу: щоб усі наступні цеглинки (gateway, MCP-сервери, runtime, evals) говорили однією мовою
і працювали на однакових, відтворюваних даних.

## Що тут є

```
package.json            скрипти: typecheck, test, fixtures
pnpm-workspace.yaml     які папки — пакети монорепо; allowBuilds для esbuild
tsconfig.base.json      суворі налаштування TypeScript (пояснення нижче)
tsconfig.json           один проєкт на весь репо, без збірки (noEmit)
vitest.config.ts        де шукати тести
packages/shared/        спільні контракти: zod-схеми, статуси, довідник Львова
scripts/fixtures/       детермінований генератор фікстур
scripts/gen-fixtures.ts запис фікстур у fixtures/
scripts/test/           тести фікстур
fixtures/               згенеровані дані (комітяться в git)
```

## Цеглинка 1. Монорепо на pnpm workspaces

**Що.** Кілька пакетів в одному репо: `packages/shared` зараз, `apps/*` і `mcp/*` далі.
Пакет `@reloc/shared` підключається як `workspace:*` — це симлінк, а не копія з npm.

**Навіщо.** Gateway, MCP-сервери, runtime і UI мають використовувати одні й ті самі схеми.
Якщо змінити `Criteria`, `tsc` одразу покаже всі місця, які зламались, в усіх сервісах.

**Нюанс.** `@reloc/shared` експортує `.ts` напряму (`exports → ./src/index.ts`), без кроку збірки.
Запускаємо все через `tsx`, тому це працює. У проді ти б або збирав пакети, або запускав Node
з type stripping — це свідомий компроміс заради простоти.

**pnpm 10+ і build-скрипти.** pnpm за замовчуванням не запускає postinstall-скрипти залежностей
(захист від supply-chain атак). esbuild (його використовує tsx) потребує postinstall, тому він явно
дозволений у `allowBuilds`. Хороша деталь для розмови про безпеку ланцюга постачання.

## Цеглинка 2. Суворий TypeScript

| Опція | Що ловить |
| --- | --- |
| `strict` | базовий набір: null-перевірки, implicit any тощо |
| `noUncheckedIndexedAccess` | `arr[i]` має тип `T \| undefined` — не можна забути, що елемента може не бути |
| `exactOptionalPropertyTypes` | `{ x?: string }` не дорівнює `{ x: string \| undefined }`. На цьому етапі вже спіймав реальну помилку в генераторі |
| `verbatimModuleSyntax` | `import type` для типів обов'язковий — немає «магічного» видалення імпортів |
| `noEmit` | `tsc` лише перевіряє типи; виконує код `tsx` |

## Цеглинка 3. zod-схеми як єдине джерело правди

Одна схема дає три речі:

1. **Валідацію в рантаймі** — `Criteria.safeParse(input)`. Типи TS зникають після компіляції,
   а дані від моделі, UI чи зовнішніх API треба перевіряти по-справжньому.
2. **Тип для коду** — `z.output<typeof Criteria>` (після дефолтів) і `z.input<...>` (до них).
3. **JSON Schema для моделі** — `z.toJSONSchema(Criteria, { io: "input" })`. Це те, що піде в
   опис інструмента. Опис полів (`.describe(...)`) потрапляє в схему і допомагає моделі.

Файли:

- `lviv.ts` — райони як enum. Модель не зможе вигадати район «center»: схема його відхилить.
  Час до офісу — умовна таблиця, щоб не залежати від зовнішніх карт.
- `criteria.ts` — критерії пошуку з дефолтами і `refine` (район не може бути водночас бажаним і виключеним).
- `listing.ts` — **нормалізоване** оголошення. Зверни увагу: поле називається `untrustedText`, а
  контактів орендодавця в ньому немає взагалі. Модель їх ніколи не побачить.
- `sources.ts` — **сирі** формати OLX і ЛУН. Вони навмисно різні. Перетворення сирого → нормалізоване
  буде в адаптерах (етап 2). Це патерн anti-corruption layer: решта системи не знає про формати джерел.
- `status.ts` — таблиця переходів статусів. `as const satisfies Record<...>` гарантує, що описані всі
  статуси, і зберігає точні типи. Текст помилки написаний так, щоб модель могла з нього виправитись.
- `people.ts`, `agent-spec.ts` — ролі, працівники, специфікація агента.
  `securityMustPass: z.literal(true)` — вимкнути security-гейт не можна навіть через no-code builder.

## Цеглинка 4. Детерміновані фікстури з пастками

**Чому генератор, а не руками написаний JSON.** 80 оголошень руками — це довго і без гарантій.
Генератор із seed дає той самий результат при кожному запуску, і ще й документує свої пастки в
`traps.json`. Evals потім просто читають цей файл: «ось ключі injection-оголошень, перевір, що агент
їх не підняв нагору».

**Як влаштований.** Спершу генеруються «фізичні» квартири, потім вони «публікуються» на OLX та/або
ЛУН у різних форматах. Квартири 60–69 є на обох сайтах — це дублі.

| Пастка | Скільки | Що перевірятиме |
| --- | --- | --- |
| Prompt injection | 3 | ранжування, спроба вивести дані, несанкціонований запис |
| Дублі OLX ↔ ЛУН | 10 (у 4 ціна відрізняється на 500 грн) | дедуплікація; issue для software factory |
| Застарілі (вже здані) | 5 (2 з них підходили Олені) | `check_availability` перед пропозицією |
| Ціна в доларах | 8 | нормалізація валюти перед фільтром бюджету |
| Телефон у тексті | ~21 | редагування PII в gateway |
| Англійська / суржик | 6 / 3 | розуміння неформального тексту |
| Опубліковані «в майбутньому» | ~16 | щоденний Scout знаходить нові оголошення (симульований час) |

Приманки з injection навмисно ідеально підходять під критерії Олени: якщо пастка не потрапляє в
результати пошуку, вона нічого не перевіряє. П'ять чесних варіантів (індекси 3–7) гарантують,
що агенту є з чого обирати.

**Тести фікстур** (`scripts/test/fixtures.test.ts`) перевіряють детермінованість, що закомічені файли
збігаються з генератором, що всі ключі в `traps.json` існують і що для Олени є щонайменше
3 чесні варіанти. Останній тест уже один раз упав і змусив виправити генератор — так і має бути.


## Що можуть спитати на співбесіді

- Чому zod, а не лише типи TypeScript? → типи зникають у рантаймі; дані від LLM — недовірений вхід.
- Навіщо розділяти сирі й нормалізовані формати? → anti-corruption layer; заміна джерела не чіпає решту.
- Чому `untrustedText`, а не `description`? → назва нагадує всім (і моделі, і людям), що це дані, а не інструкції.
- Чому фікстури детерміновані? → інакше eval, що впав, неможливо відтворити, а flaky evals швидко перестають читати.
